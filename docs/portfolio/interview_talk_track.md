# 面试讲解候选稿

## 30 秒版

我做了一个经营分析 Agent，把重复的 GMV 周期比较、贡献拆解和报告整理变成可追踪流程。LLM 只理解问题、选合法路径和组织已验证结论；计算和证据边界由程序控制。我接入了约 147 万行真实历史交易，并保留渠道不支持时的安全停止示例。当前是个人原型，评测失败和不支持能力都明确记录。

## 2 分钟版

这个项目解决的是重复经营分析中的一致性问题。仅让模型写 SQL 和报告，很难保证每次使用相同口径、贡献能闭合，以及解释没有越过证据。我将 Knowledge、Skill、Workflow、Runtime 和 Tool 分开，用 JSON 维护语义，通过七个 Skill 和显式状态机执行诊断。模型遇到多个合法候选才参与选择，唯一候选直接由程序决定。

真实数据采用 Complete Journey，约 147 万行交易。难点不是读入 SQLite，而是明确 sales_value 代表零售商收到的商品销售金额，并不等于顾客自付金额；交易有效性来自批准的来源契约，没有造 payment_success 列。数量存在混合单位，因此更深数量分析停止。渠道字段不存在时，即使理解了问题也必须 blocked。

评测分离离线计算、Live 行为和 Provider 可用性。曾发现 Intent schema 丢失维度偏好，修复后回归 16/20 通过，但仍有错误维度偏好等失败；使用过的 Holdout 已明确改称回归集。Gemini 服务不稳定时只有限重试，报告使用已验证结果回退。下一步生产化会先完善契约版本、访问控制和独立新评测，而不是继续增加 Agent 数量。

## 5 分钟深挖版

**问题与取舍。** 经营分析经常重复比较本期基期、找主要贡献来源、下钻并写结论。我希望让这些动作可复核。因此项目采用规范驱动的有限流程，而不是追求开放式自主规划。业务范围先固定为 GMV。

**执行链路。** 问题先转成包含周期、指标、过滤和维度偏好的 Workflow Input。数据映射与能力检查通过后，Runtime 更新正式 State，调用比较、异常、分解、贡献和下钻 Skill。差值、乘法贡献、方向对齐、闭合、排序、覆盖与停止条件都是确定性程序。多个合法候选需要语义判断时，模型只允许选候选或 no_valid_choice。Evidence Validation 之后才构建结果；报告目前仅编排已有 Claim，限制和状态由程序保留。

**真实数据困难。** 接入 Complete Journey 时保留了全部 1,469,307 行，商品 left join 不丢失未匹配记录，缺失品类标 unknown。basket 对应购买场次，gross_gmv 使用经过批准的零售商商品销售所得口径。家庭 ID 不是个人客户，观察期首购也不等于生命周期新客。数量尺度无法证明一致，因此保留原值而不开放数量相关指标。两次 SQLite 构建哈希一致，金额核对一致。

**演示结果。** 2017 年 1 月到 12 月 GMV 从 370,886.93 到 421,882.29，AOV 占同向根贡献 77.79%。进一步数量拆解不可用，所以 root 是 partial。请求 category 可走合法 GMV 品类贡献；请求 channel 被识别但能力检查 blocked，没有任何核心 Claim。AOV 或类别的内部贡献不证明促销、竞争等外部原因。

**评测与一次修复。** 先用合成 SQLite 和 Mock 验证确定性链路，再跑 Live，Expected 不进入运行请求。早期共享 schema 没保存维度 context，修复后请求品类等偏好可以进入 Runtime。但回归仍出现额外 customer_type 偏好使路径偏离需求，说明合法路由不等于正确理解问题。最终 16/20 通过，路径 17/19，嵌套 Driver 2/4；Evidence 52/52 是引用覆盖，不证明所有分析正确。另一个失败来自 -8.8% 未达到冻结阈值却被 Expected 要求深挖，历史没有为了好看而修改。这个集合已暴露，不能再称未见 Holdout。

**可靠性和下一步。** Gemini 曾有 429/503/504。限制应用重试、避免 SDK 重试叠加，报告失败只从 structured result 回退，不替意图失败编造输出。DeepSeek 当轮请求全部成功不代表长期服务保证。当前是本地单表分析原型；生产化优先做数据权限、质量监控、契约版本与容量测试，并以独立新场景检验泛化。不会将这些未来计划写成已交付能力。
