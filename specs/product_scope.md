# 数据分析 Agent 项目基线：对象定位、职责与边界

> **版本**：Product Scope v1.0  
> **状态**：已确定 / 作为后续设计基线  
> **适用范围**：数据分析 Agent 项目第一阶段  
> **原则**：后续的功能设计、架构设计、Workflow、工具选择与评测方案默认不得偏离本文档；如需改变服务对象、核心职责或职责边界，应先显式更新本文档版本。

---

## 1. Agent 服务对象

### 1.1 主要服务对象

**业务运营 / 经营运营 / 对业务单元 KPI 负责的运营或业务负责人。**

该类用户通常需要持续关注业务经营结果，并围绕指标变化完成日常分析、问题定位和汇报工作。

### 1.2 典型工作特征

主要包括：

- 持续查看经营数据；
- 监控核心 KPI 的变化；
- 发现异常指标；
- 对异常指标进行拆解；
- 定位变化主要发生在哪些渠道、商品、用户、地区等维度；
- 制作日报、周报、月报；
- 回答临时经营问题；
- 根据数据分析结果推进后续业务动作。

### 1.3 Agent 优先替代的工作类型

Agent 不以替代整个运营岗位为目标，而是优先自动化以下类型的工作：

> **高频、重复、规则相对稳定、数据驱动、人工操作繁琐的经营分析流程。**

重点包括：

- 重复取数；
- 日常经营巡检；
- 指标同比 / 环比 / 同期对比；
- 基础指标拆解；
- 多维度下钻；
- 变化贡献度分析；
- 数据证据整理；
- 日报 / 周报等基础汇报整理。

## 2. Agent 定位

### 2.1 产品定位

**经营监控与诊断 Agent**

英文暂定：

**Business Performance Agent**

### 2.2 定位方式

Agent 按照一种可重复执行的**经营分析工作任务**进行定义，而不是绑定某个具体行业或某一种运营岗位。

第一阶段可以使用**电商 / 零售业务**作为 Reference Implementation（参考实现），用于承载数据模型、指标体系和 Demo 场景。

但核心能力应尽量设计为可迁移：

- 电商 / 零售；
- SaaS；
- 游戏；
- O2O；
- 其他具备明确经营指标体系的业务。

### 2.3 产品形态

本项目**不是**以“通用聊天式 Data Analyst”作为第一阶段目标。

核心形态应是：

> **可重复执行的经营巡检、异常发现、指标拆解、贡献定位和结果汇报 Workflow。**

临时自然语言经营问答可以作为能力之一，但不应取代自动巡检与诊断成为产品核心。

---

## 3. Agent 核心职责

Agent 第一阶段负责以下能力。

### 3.1 自动读取经营数据

从预先接入的数据源获取分析所需数据，并按照既定指标口径进行处理。

### 3.2 监控核心经营指标

持续检查核心 KPI，包括其当前值、同比 / 环比 / 同期变化及其他预设比较基准。

### 3.3 识别异常变化

根据预设规则、统计阈值或分析逻辑判断某项指标是否值得进一步诊断。

### 3.4 指标拆解

根据指标之间的业务关系，将异常指标拆解为更底层的驱动因素。

例如：

```text
GMV
├── Orders
└── AOV
```

### 3.5 多维度 Drill-down

围绕异常进一步定位变化主要发生在哪些业务维度，例如：

- 新客 / 老客；
- 渠道；
- 商品；
- 品类；
- 地区；
- 设备；
- Campaign；
- 其他预定义业务维度。

### 3.6 计算变化贡献度

区分“某个维度发生了变化”和“该变化对总指标异常贡献有多大”。

Agent 应优先识别对总体变化贡献最大的因素，而不是简单枚举所有波动。

### 3.7 验证内部数据证据

所有核心结论都应尽可能绑定可验证的数据证据。

Agent 不应在没有数据支持时补充确定性解释。

### 3.8 生成经营摘要与基础报告

将监控、异常和诊断结果整理成可供运营快速阅读的内容，包括：

- 经营概览；
- 核心异常；
- 主要贡献因素；
- 数据证据；
- 尚未解决的问题；
- 需要人工补充的业务背景。

典型输出形式包括：

- 日报；
- 周报；
- 异常诊断摘要；
- 临时经营问题分析结果。

### 3.9 响应临时经营问题

支持用户针对当前业务提出临时分析问题，并调用同一套指标定义、拆解逻辑和数据工具进行分析。

但该能力属于经营分析 Workflow 的扩展，而不是一个独立的通用聊天机器人目标。

## 4. Agent 职责边界

### 4.1 Agent 可以回答的问题

Agent 的核心责任是回答：

> **发生了什么？**

> **变化主要发生在哪里？**

> **内部数据能够证明哪些因素贡献最大？**

例如：

> Paid Search 新客订单下降贡献了本次 GMV 下滑的 63%。

如果该结论能够由内部数据计算得到，则属于 Agent 的职责范围。

---

### 4.2 Agent 不负责无证据的外部因果判断

Agent 不应仅根据内部经营结果直接宣称：

- 竞争对手行为导致指标变化；
- 市场环境导致指标变化；
- 用户心理变化导致指标变化；
- 广告平台机制变化导致指标变化；
- 供应链事件导致指标变化；
- 其他数据库中没有证据支持的外部原因。

例如：

> “Paid Search 新客订单下降 31%。”

属于数据事实。

但：

> “Paid Search 下滑是因为竞争对手提高了竞价。”

如果没有额外证据，则不能作为确定结论输出。

---

### 4.3 不把贡献分析包装成因果推断

Agent 必须区分：

**贡献定位**

与

**因果解释**

前者可以基于内部数据计算，例如：

> 某渠道贡献了总体 GMV 下滑的 52%。

后者需要额外的因果证据，例如：

> 某渠道下滑是因为竞品降价。

第一阶段 Agent 的主要能力集中在前者。

---

### 4.4 不直接代替运营完成最终业务决策

Agent 第一阶段不直接决定：

- 是否降价；
- 是否打折；
- 是否增加 / 减少广告预算；
- 是否下架商品；
- 是否调整库存；
- 是否改变渠道策略；
- 是否执行其他高影响业务动作。

Agent 可以提供：

- 数据事实；
- 变化贡献；
- 内部证据；
- 待验证问题。

最终决策由人工结合真实业务约束完成。

---

### 4.5 不擅自扩张分析范围

如果当前数据无法支持某个问题，Agent 应明确说明：

- 当前数据能够确认什么；
- 当前数据无法确认什么；
- 还需要哪些额外信息。

不得为了形成完整故事而自行补充未经验证的解释。

---

## 5. 人机分工

### 5.1 Agent 负责

```text
发现异常
→ 数据拆解
→ 多维定位
→ 计算贡献度
→ 验证内部证据
→ 输出诊断结果
```

### 5.2 人工运营负责

```text
补充业务背景
→ 判断外部真实原因
→ 结合经营约束
→ 权衡不同方案
→ 做最终业务决策
```

### 5.3 分工原则

Agent 的价值主要位于：

> **决策之前的高频分析与信息整理环节。**

第一阶段不追求自动替代完整经营决策链。

---

## 6. 产品原则

### 6.1 自动化优先级

优先自动化同时满足以下条件的流程：

1. 高频；
2. 重复；
3. 规则相对稳定；
4. 数据驱动；
5. 人工步骤繁琐。

### 6.2 Workflow 优先于 Chatbot

核心能力优先围绕：

```text
经营指标
→ 自动巡检
→ 异常识别
→ 指标拆解
→ 维度定位
→ 贡献度分析
→ 证据验证
→ 经营摘要
```

而不是：

```text
用户提问
→ LLM 回答
```

### 6.3 分析逻辑与行业数据解耦

系统应尽量将以下内容分离：

**通用分析能力**

- 异常检测；
- 指标拆解；
- 维度下钻；
- 贡献度计算；
- 证据验证；
- 报告生成。

**行业配置**

- 指标定义；
- 指标关系；
- 业务维度；
- 数据 Schema；
- 业务规则。

目标是通过替换行业配置，使核心 Agent Workflow 可以迁移。

## 7. 第一版行业实现

### 7.1 Reference Implementation

第一版优先采用：

**电商 / 零售经营场景**

原因不是将 Agent 定义为“电商 Agent”，而是该场景具有较完整的经营分析链路，适合作为第一阶段验证环境。

典型链路可以包括：

```text
Traffic
→ Visitor
→ Product View
→ Cart
→ Checkout
→ Order
→ Payment
→ Repeat
```

可使用的业务维度包括：

- Channel；
- Product；
- Category；
- Region；
- Customer；
- Device；
- Campaign。

### 7.2 后续迁移原则

未来如果迁移到 SaaS、游戏、O2O 等场景，应优先替换：

- Metric Definition；
- Decomposition Tree；
- Dimensions；
- Business Rules；
- Schema。

而不是重写整个 Agent Workflow。

## 8. 后续设计的硬约束

后续任何 Agent 设计默认遵守以下约束：

1. **服务对象不漂移**：第一阶段首先服务经营运营人员，而不是试图同时覆盖分析师、产品经理、管理层等所有角色。
2. **核心目标不漂移**：优先解决经营巡检、异常定位、基础归因和报告整理。
3. **不退化为 NL2SQL Demo**：自然语言查询数据库只能是工具能力之一。
4. **不追求无边界“智能”**：所有自动诊断必须能够回到业务指标、计算过程或数据证据。
5. **贡献分析与因果推断分离**。
6. **最终业务决策保留人工责任**。
7. **优先建立可重复执行的 Workflow，再增加复杂 Multi-Agent 架构。**
8. **第一阶段架构选择必须服务上述业务目标，而不是为了展示 Agent 技术而增加复杂度。**
9. **如后续功能与本文档发生冲突，应优先检查是否出现 Scope Creep（范围蔓延）。**
10. **若需要改变服务对象、职责或边界，应先更新本基线文档，再继续设计。**

---

## 9. 一句话项目定义

> **面向业务运营人员的经营监控与诊断 Agent，通过自动读取经营数据、监控核心指标、识别异常、执行指标拆解和多维度贡献分析，并生成经营摘要与基础报告，减少运营人员在重复取数、经营巡检、基础归因和汇报整理上的时间；Agent 负责定位内部数据所能证明的变化来源，外部因果判断及最终业务决策保留给人工。**

---

## 10. 当前冻结项

截至 Product Scope v1.0，以下内容视为已经确定：

- **Primary User**：业务运营 / 经营运营人员；
- **Product Positioning**：经营监控与诊断 Agent；
- **核心价值**：替代高频重复的经营分析流程；
- **核心 Workflow**：监控 → 异常 → 拆解 → 定位 → 贡献 → 证据 → 汇报；
- **第一版 Demo Domain**：电商 / 零售；
- **Agent 能力边界**：内部数据事实与贡献诊断；
- **人工保留职责**：外部因果判断、业务权衡和最终决策。

后续产品设计应以本节作为最简检查表。
